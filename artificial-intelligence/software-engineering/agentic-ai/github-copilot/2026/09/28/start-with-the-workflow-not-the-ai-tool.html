Series — AI-Native SDLC with GitHub Copilot · Part 01
The strongest AI adoption programs do not begin with a feature checklist. They begin by understanding how engineering work actually happens.

GitHub Copilot can help explain code, draft documentation, generate tests, edit files, operate in the terminal, and participate in increasingly agentic workflows. None of those capabilities automatically tells us where AI will create meaningful value.

That decision starts earlier.

Before choosing chat, agent mode, CLI automation, skills, hooks, MCP servers, or a custom integration, we need to understand the workflow itself: where engineers spend time, where context is lost, which tasks repeat, where decisions stall, and which outcomes matter to the team.

This first part establishes the discovery discipline that the rest of the series will build on.

1. Why workflow comes before tooling

A common AI-adoption mistake is to start with the product surface:

  • Which Copilot features do we have?
  • Should we create an agent?
  • Do we need an MCP server?
  • Should the team create reusable skills?
  • Can we automate pull requests?

Those are useful questions later. At the beginning, they can cause us to automate the wrong thing.

A better sequence is:

flowchart LR
    A[Observe real work] --> B[Map the workflow]
    B --> C[Identify friction]
    C --> D[Find AI-suitable opportunities]
    D --> E[Prioritize by value]
    E --> F[Pilot one workflow]
    F --> G[Measure outcomes]

The objective is not to maximize the amount of AI in the process. It is to improve the engineering system.

Typical areas worth observing include unfamiliar repositories, repetitive boilerplate, documentation gaps, issue triage, pull-request preparation, test generation, and context switching. These are useful starting points because the work is visible enough to inspect and the cost of friction can often be measured.

2. Observe the work as it actually happens

Discovery should describe the current system, not the ideal process written in a handbook.

Watch a real workflow from beginning to end. For example, take one engineer handling an unfamiliar issue in an existing repository:

  1. read the issue;
  2. locate the relevant repository and service;
  3. understand project structure;
  4. find related code;
  5. trace data flow;
  6. reproduce the problem;
  7. decide on a change;
  8. implement it;
  9. run tests;
  10. prepare a pull request;
  11. respond to review feedback.

At every step, capture four things:

Dimension Question
Time Where is time being lost?
Friction Where does the engineer get stuck or repeat work?
Context What information has to be rediscovered or moved between systems?
Outcome What visible engineering or business result does this step influence?

Do not assume every slow step should be automated. Some steps are slow because they require judgment. The discovery exercise is about distinguishing mechanical friction from valuable thinking.

3. Build a developer-journey map

The developer journey makes hidden transitions visible.

flowchart LR
    I[Issue] --> R[Repository]
    R --> U[Understand]
    U --> P[Plan]
    P --> C[Change code]
    C --> T[Test]
    T --> PR[Prepare PR]
    PR --> V[Review]
    V --> M[Merge]

    U -. friction .-> U1[Missing docs\nUnknown architecture]
    T -. friction .-> T1[Test setup\nEdge cases]
    PR -. friction .-> P1[Summaries\nChecklists]

This diagram is intentionally simple. The goal is not architecture documentation; it is workflow visibility.

Once the journey exists, interview developers and stakeholders around concrete transitions:

  • Which step takes longer than it should?
  • Which work is repeated across issues or repositories?
  • Where do people leave the IDE to search for context?
  • Which tasks have a predictable input and output?
  • Where are mistakes expensive?
  • Which improvement would be visible to the team or customer?

These questions help separate a compelling demo from a useful engineering capability.

4. Turn friction into AI opportunities

Not every friction point needs the same Copilot capability.

A useful first-pass mapping is:

Friction Potential capability Why it may fit
Understanding an unfamiliar codebase Chat / agent-assisted exploration Contextual explanation and repository navigation
Repetitive documentation Prompt or reusable skill Predictable structure and repeatable output
Local scripts and shell work Copilot CLI Natural-language terminal assistance
Issue-to-change workflow Agent mode Bounded multi-step work across files
Internal systems or live data MCP-enabled tools Access to approved external capabilities
Repeated team workflow Skill / agent / shared instruction Reuse and consistency

The important word is potential.

Capability selection belongs after the problem is understood. The same friction may have a simpler solution: better documentation, a shell script, a template, a build fix, or removing an unnecessary approval.

5. Prioritize value instead of novelty

For the lab, we will score opportunities using five dimensions:

  • Frequency — how often the workflow occurs.
  • Friction — how much delay, repetition, or cognitive load it creates.
  • AI suitability — whether the work can be assisted with reliable context, tools, and validation.
  • Outcome visibility — whether improvement can be measured.
  • Risk — whether mistakes could create security, compliance, quality, or operational problems.

A lightweight score can help compare opportunities without pretending that the score is scientific truth:

Opportunity score =
  frequency
+ friction
+ AI suitability
+ outcome visibility
- risk

Use the number to provoke discussion, not to replace judgment.

A high-value first pilot normally has a bounded scope, trusted context, a clear success condition, and an output a human can verify.

6. Establish a measurable baseline

If we want to know whether AI helped, we need a baseline before the pilot.

Possible measures include:

  • time to understand an unfamiliar repository;
  • issue-to-first-implementation time;
  • pull-request preparation time;
  • cycle time;
  • time to first meaningful contribution for a new engineer;
  • test-writing time;
  • defect or rework rate;
  • number of manual context switches;
  • developer confidence or satisfaction for the target workflow.

The baseline does not need to become a giant metrics program. Part 01 needs only enough evidence to compare the pilot with the previous way of working.

flowchart LR
    U[Usage] --> A[Adoption]
    A --> E[Engineering outcome]
    E --> T[Team capability]
    T --> B[Business value]

Usage by itself is not the goal. A large number of Copilot interactions can coexist with no meaningful improvement in delivery, quality, learning, or customer outcomes.

8. What we carry into Part 02

Part 01 intentionally does not start by creating an agent, an MCP server, or a RAG layer.

We first establish:

real workflow
    ↓
observable friction
    ↓
valuable AI opportunity
    ↓
measurable baseline

Part 02 can then ask a much better question:

What context must Copilot receive — from the developer, repository, team, organization, product knowledge, and external systems — to assist this workflow well?

That is where context engineering begins.

Key takeaway

Start with the workflow, not the AI tool.

Understand the work, locate the friction, choose a bounded opportunity, and establish how success will be measured. Only then select the Copilot capability and supporting AI assets.
